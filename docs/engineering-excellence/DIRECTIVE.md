You are the engineering orchestrator, not a solitary coding assistant. ## 4. Engineering standards: optimization is not operator counting

Optimize **work, latency, memory traffic, and resource lifetimes**, not the number of Rust operators or lines. Never replace a readable expression merely to reduce arithmetic operations without demonstrating an actual relevant benefit. LLVM may already optimize both forms identically. A branchless implementation can be slower, and a manual SIMD routine can be worse on some architectures. A heap allocation removed by a massive inline buffer can increase working-set size and cache misses. A shorter function can hide an expensive allocation or broad traversal. An abstraction can be zero-cost or can introduce indirection and code bloat: determine which.

Order of investigation: avoid work entirely; use an appropriate complexity class and workload boundary; choose data-oriented storage and improve locality; eliminate repeated invariant calculations and copies; reuse allocations; reduce synchronization and blocking I/O; batch and amortize; parallelize independent expensive work deterministically where appropriate; profile and consider vectorization, layout, branch behavior or instruction-level tuning only after identifying a real hotspot. Use representative release code, not debug speed. Benchmark changes individually or against controlled groups. Inspect generated assembly, compiler IR or hardware counters where useful, not as mandatory ceremony. Prefer stable Rust and safe APIs; new unsafe only with documented local invariants, proof of necessity, scoped independent review, and applicable safety tooling. Do not add a dependency to avoid writing ten clear lines, nor reimplement mature complex primitives for vanity. Evaluate dependency cost, security maintenance, licensing, cross-platform behavior, runtime and build footprint, and alternatives. Favor simple, well-understood algorithms until scale justifies complexity.

Never relax authoritative determinism by enabling unsafe floating-point transformations or approximate semantics unnoticed. Distinguish logical state, derived/cache state and cosmetic presentation. Visual approximation, LOD, temporal reuse, and GPU nondeterminism may be acceptable **where semantically cosmetic** and quality evidence meets the declared visual contract. Never silently discard authoritative obligations, committed consequences, saves, identities, memories, impacts or required work. Budget exhaustion must be observable, make progress and have documented handling. Preserve full visual quality and workload at the reference comparison; add optional quality/performance tiers only as deliberate features, not as a way to hide regressions. Do not remove significant functionality to reduce LOC, binary size, test counts or benchmark time.

Use checked boundary contracts and explicit finite numerical domains. Validate expensive immutable data once at admission where safe; do not revalidate the whole invariant state on every hot-path operation merely because it is easy. Retain checks needed for untrusted input. Favor typed error/status distinctions over strings where they form reusable API contracts. Define overflow/underflow, identity lifetime, ordering, atomicity, cancellation, capacity and saturation behavior. Fail closed on authority and corruption; fail visibly on resource refusal. Make error paths maintainable, not just success paths short.

## 6. Expanded audit — additional findings and investigation leads

These supplement, rather than replace, A01–A25. A confirmed source observation is distinct from a measured runtime bottleneck or an executed correctness reproducer. Verify hypotheses by minimal reproducer before marking as confirmed. All source links can be constructed against `https://github.com/Willpatpost/PostRust/blob/5b9316742b2f9fe4d0fca2a9743275f91a2ff6aa/` plus path.

**B01 — Scheduler budget is execution-count-only (confirmed structural gap).** `core/spine.rs::drain_due` (~1767) loops until `executed < cap`; moving a due event into `blocked` does not increment executed. One tick can therefore process arbitrarily many due blocked events relative to the execution cap. `execute_now` (~1908) releases all waiters synchronously, and `try_unblock` (~1953) checks the dependent's full dependency list each time. High fan-in/fan-out may multiply cost. Follow-up scheduling also needs explicit workload boundaries. Preserve the guarantee on actual executions and near/far fairness, while accounting for queue housekeeping, dependency transitions, fan-out and bounded continuation work. Do not drop dependencies or change observable order without deliberate compatibility/migration. Evaluate remaining-dependency counts and indexed waiters against adversarial graphs; ensure no starvation/deadlock. Work is not bounded just because handler count is bounded.
