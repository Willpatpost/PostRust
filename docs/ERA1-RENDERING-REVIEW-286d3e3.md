## Vulkan correctness and frame ownership

### 1. BLOCKING — Both capture paths omit device-to-host visibility

The shadow path copies depth into a mapped buffer and waits on the submission fence before copying the floats into Rust. The color path does the same for bytes. Its post-copy barrier transitions the **image** back for presentation and gives the destination **buffer** no host-read dependency. The fence establishes completion. Vulkan explicitly requires a memory dependency to make device writes visible to host access. Coherent memory removes explicit cache invalidation from this path. On a conforming implementation the host can therefore read stale data after a successful wait. All five pixel gates depend on color capture, and the PCF oracle also consumes the depth capture. [shadow_draw.rs:841](https://github.com/Willpatpost/PostRust/blob/286d3e32ba41e79487619497f49a9bdd802ed72a/crates/engine-renderer/src/shadow_draw.rs#L841) · [shadow_draw.rs:865](https://github.com/Willpatpost/PostRust/blob/286d3e32ba41e79487619497f49a9bdd802ed72a/crates/engine-renderer/src/shadow_draw.rs#L865) · [vulkan.rs:3934](https://github.com/Willpatpost/PostRust/blob/286d3e32ba41e79487619497f49a9bdd802ed72a/crates/engine-renderer/src/vulkan.rs#L3934) · [vulkan.rs:3950](https://github.com/Willpatpost/PostRust/blob/286d3e32ba41e79487619497f49a9bdd802ed72a/crates/engine-renderer/src/vulkan.rs#L3950) · [vulkan.rs:2752](https://github.com/Willpatpost/PostRust/blob/286d3e32ba41e79487619497f49a9bdd802ed72a/crates/engine-renderer/src/vulkan.rs#L2752) · [Vulkan fence waits](https://docs.vulkan.org/spec/latest/chapters/synchronization.html#synchronization-fences-waiting)

### 2. BLOCKING — Shadow readback can consume the wrong frame or buffer

The API promises the next **shadowed** frame and creates shadow resources when the request is made. Recording consumes the request whenever those resources exist. A plain frame in between can copy an unwritten or older map while declaring its old layout to be `SHADER_READ_ONLY_OPTIMAL`. Separately, taking a completed capture looks up the current shadow state. Pipeline replacement constructs another `Some(shadows)` and destroys the original buffer. The old frame's fence can succeed while the host reads the fresh allocation. The `.ok()?` on the fence wait also converts a timeout or device error to `Ok(None)` and the caller clears readiness. ### 4. BLOCKING — Post and reflection violate the negotiated depth format

The selector admits D32, D24/S8 and D16. The HDR render pass declares the selected format, but the post image-view helper chooses `DEPTH` only for D32 and `COLOR` for every other format. The reflection framebuffer always supplies a D32 view to that same HDR pass. On a fallback device, post requests an invalid aspect and reflection supplies an attachment of a different format. For D24/S8 the HDR attachment also leaves `stencil_load_op` at its default `LOAD` with an `UNDEFINED` initial layout. The successful D32 path hides all three. ### 5. BLOCKING — Shadowed wet ground reads a camera block its frame never writes

The shadowed entry point supplies extended shadow parameters and no ordinary corner parameters. The depth pass writes the extended buffer. In both the swapchain and HDR passes, only the ordinary lighting branch writes the corner buffer. The wet ground descriptor binds that **corner** buffer at the slot's dynamic offset. On first use its camera bytes are uninitialized. After a plain frame they can contain a previous pose. The reflected scene can be correct while the ground redraw misses `EQUAL` depth or computes Fresnel from an old eye. Current composition coverage renders and discards the shadowed capture. ### 6. SHOULD-FIX — The first frame after pipeline replacement can lose whole passes

Active sky, wet state, and the shadowed/sky HDR variants are ensured **before** either site that can replace the pipelines. The replacement rebuilds shadows and base post, then the current frame proceeds with the new objects. Recording silently skips missing sky and wet state. ### 7. SHOULD-FIX — A retired swapchain view handle serves as a cache generation

The post cache compares the extent and the numerical first swapchain view. The bundle owns a framebuffer for *each* old view, later indexed by the new image index. An inactive post chain can retain that bundle across multiple same-format recreations. Once an old view has been destroyed, Vulkan permits handle reuse. Returning to the same extent can produce a cache hit on a retired framebuffer set. A larger new image count can also put the index past the vector. ### 11. SHOULD-FIX — Sedan wheel sides and one cap disagree with their normals

At the top of a wheel, the first side edge runs along +X and the next ring point advances toward +Z. Their cross product points inward while the supplied radial normals point outward.
